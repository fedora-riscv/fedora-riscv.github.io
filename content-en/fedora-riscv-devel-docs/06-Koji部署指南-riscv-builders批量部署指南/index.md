# 0. Prerequisite: a koji-hub system

Please refer to the separate document "Koji Deployment Guide - Kojihub Deployment".

This document focuses on adding RISC-V builders to an already running koji system.

However, some files must be named according to a set of rules so that the automatic deployment scripts and the certificate scripts can be used together. The following are some provisional rules, "__TekkamanV1.0__":

- The connector is '_', to avoid '-' being treated as an operator.

## a. Builder numbering rules:

- **The number [num] is a three-digit decimal number:**
  
  - The first digit denotes the server number \<S>,
    
    - The qemu builders in koji builder server 1 are numbered 1xx
    - The koji-hub server has number 0, so the qemu builders in it are numbered 0xx. The builders there are generally used for testing and for building Images (in the “appliance” channel).
  
  - The last two digits denote the qemu builder number \<NN>
    
    - 00～89: qemu builder in **default channels**
    
    - __90～99:__ qemu builder in some other channels, like “appliance”
  
  - The number of a mock builder is \<S>M\<N>__, where M stands for Mock__

## b. Naming rules for the CN (Common Name) in certificates

**[type]\_[arch]\_[num].[subdomain].[domain]**

type: buildvm, buildhw, buildmk

arch: riscv64, ......

num: 001, ......

For example, OpenKoji: [https://openkoji.iscas.ac.cn](https://openkoji.iscas.ac.cn/)

buildvm_riscv64_001.openkoji.iscas.ac.cn

## c. Builder naming rules:

**This name is used when adding the builder to kojihub, and must be consistent with the certificate CN.**

[type]\_[arch]_[num].[subdomain].[domain]

- Koji builder naming example: buildvm_riscv64_000.openkoji.iscas.ac.cn
- Mock builder naming example: buildmk_riscv64_0M0.tekkamanv.com

## d. Builder certificate file naming rules:

To better identify certificate files during automatic deployment, the certificate file names generated by the scripts are uniformly:

- __Client certificate:__ [type]\_[arch]_[num].[subdomain].[domain].pem
  - That is, __<certificate CN>.pem__
- __CA certificate:__ [servername]\_ca_cert.crt, by default: koji\_ca_cert.crt

To unify the Image configuration files, the paths on the builder are kept at the default configuration:

- **Client certificate:** /etc/kojid/client.crt
- **CA certificate:** /etc/kojid/serverca.crt

## e. Builder Image naming rules:

Only buildvm uses Image files, and all of them are deployed under [subdomain].[domain], so these parts can be omitted:

System Image: [arch]_[num].raw

Data Image: [arch]_[num].data.raw

# 1. Configuration on the koji-hub side

## a. Adding a builder to the system

First we need to add the builder to the system.

**Make sure this step is completed before the kojid daemon is enabled for the first time; otherwise, to make the system work properly you will have to fix it with the “--force” option** (or manually delete the records in the sessions and users tables of the database -- to be confirmed).

```shell
koji add-host <common name> <arch>
#Usage: koji add-host [options] <hostname> <arch> [<arch> ...]
#(Specify the --help global option for a list of other help options)
#Options:
#  -h, --help            show this help message and exit
#  --krb-principal=KRB_PRINCIPAL
#                        set a non-default kerberos principal for the host
#  --force               if existing used is a regular user, convert it to a
#                        host
```

- The first argument is the builder's hostname (the common name in the certificate)
- The second argument specifies the system architectures supported by the builder.

## b. Letting a builder accept specific task types

A channel is a way to control which builder can perform which type of task. By default, builders are added to the default channel. At least some builders also need to be added to the createrepo channel (for example, the koji server itself has kojid installed specifically as a repository-operations builder), so that there are builders to perform the repo creation tasks submitted by kojira.

```shell
#Usage: koji add-host-to-channel [options] <hostname> <channel>
#(Specify the --help global option for a list of other help options)
#Options:
#  -h, --help  show this help message and exit
#  --new       Create channel if needed
#  --force     force added, if possible
```

For example

- Create/update repositories
  
  ```shell
  koji add-host-to-channel <common name> createrepo
  ```

- Generate images
  
  ```shell
  koji add-host-to-channel <common name> appliance     
  ```

## c. Changing the capacity

The default capacity of a builder added to the database host table is 2. This means that if a builder's average load exceeds 2, the kojid daemon on that builder will no longer accept new tasks. This is a different control from the maximum number of tasks in the configuration file. Before accepting a task, kojid needs to check the system load and the number of tasks waiting to be executed, making sure that the average load has not exceeded the builder's average load capacity and that the number of tasks kojid has accepted and that are waiting to be executed is less than the maximum number of tasks. However, now that quad-core or even higher core-count CPUs are widely used, setting the average load to 2 cannot make full use of the hardware's performance.

**The way to change it is as follows:**

- Command-line tool:
  
  ```shell
  koji edit-host --capacity=4  localhost_x86_64
  #koji edit-host <hostname> [<hostname> ...] [options]
  #  --arches=ARCH1,ARCH2, ...,
  #  --capacity=CAPACITY  Capacity of this host
  #  --description=DESC   Description of this host
  #  --comment=COMMENT    A brief comment about this host
  ```

- Manually modifying the database:
  
  ```shell
  sudo su koji
  [koji@Samantha ~]$ psql koji
  psql (13.4)
  Type "help" for help.
  
  koji=> select (host_id, capacity) from host_config;
    row  
  -------
   (1,2)
  (1 row)
  
  koji=> update host_config set capacity = 4 where host_id = 1;
  UPDATE 1
  koji=> 
  ```

# 2. Issuing builder certificates

An example script for issuing certificates:

**cert-issue.sh:**

```shell
#!/bin/bash
WORK_DIR=/etc/pki/koji

EXPIRE_DAYS=3650
PASSPHRASE_FILE=pw.txt
SSL_CONF_TEMPLATE=openssl.conf
# if you change your certificate authority name to something else you will
# need to change the caname value to reflect the change.
caname=koji
CA_CERT_PRI_KEY=${WORK_DIR}/private/${caname}_ca_cert.key
CA_CERT_CRT=${WORK_DIR}/${caname}_ca_cert.crt

# __HOST_NAME is equal to parameter one or the first argument when you actually
# run the script
ORG_UNIT=Koji
SERVER_NAME=koji.tekkamanv.com
__ORG_UNIT=${ORG_UNIT}
__EMAIL_ADDR=${1}@${SERVER_NAME}
__HOST_NAME=${1}
__PRI_KEY=${WORK_DIR}/private/${__HOST_NAME}.key
__CSR_FILE=${WORK_DIR}/certs/${__HOST_NAME}.csr
__CRT_FILE=${WORK_DIR}/certs/${__HOST_NAME}.crt
__PEM_FILE=${WORK_DIR}/${__HOST_NAME}.pem

__COMMON_NAME=${1}
SSL_CONF_SUBJ_COM='/C=CN/ST=Guangdong/L=Shenzhen/O=TekkamanV'
__SSL_CONF_SUBJ="${SSL_CONF_SUBJ_COM}/OU=${__ORG_UNIT}/CN=${__COMMON_NAME}/emailAddress=${__EMAIL_ADDR}"


sudo openssl genrsa \
    -out ${__PRI_KEY} 2048 \
&& \
sudo openssl req -new -nodes -passin file:${PASSPHRASE_FILE} \
    -config ${SSL_CONF_TEMPLATE} \
    -subj ${__SSL_CONF_SUBJ} \
    -key ${__PRI_KEY} \
    -out ${__CSR_FILE} \
&& \
sudo openssl ca -batch -passin file:${PASSPHRASE_FILE} \
    -config ${SSL_CONF_TEMPLATE} \
    -out ${__CRT_FILE} \
    -infiles ${__CSR_FILE} \
&& \
sudo cat ${__CRT_FILE} ${__PRI_KEY}  | sudo tee ${__PEM_FILE} > /dev/null
```

- The process of issuing a builder certificate:
  
  ```shell
  sudo ./cert-issue.sh <common name>
  ```

# 3. Deploying kojid [using a localhost-deployed repository-maintenance builder as an example]

Kojid is the build daemon that runs on every Builder. It is mainly responsible for polling for build task requests sent from kojihub and handling them according to the actual situation. Besides building RPM packages, Koji also supports other task types, such as making livecd image files or raw disk image files, which can also be handled by kojid. kojid uses mock to create the original build environment, and creates a separate build environment for each build task, ensuring that the build process is not disturbed by other builds. kojid is implemented in Python and communicates with koji-hub through XML-RPC.

## a. Installation

```shell
sudo yum install koji-builder
```

## b. Configuration

- **/etc/kojid/kojid.conf - Kojid daemon configuration file**

  - __/usr/lib/systemd/system/kojid.service__
  
  - ~~/etc/sysconfig/kojid [systemV configuration file, has been removed]~~

- Key settings in /etc/kojid/kojid.conf
  
  - server: the URL of the koji hub xmlrpc interface
  
  - topurl: the URL of the koji hub file access interface
    
    ```shell
    ; The URL for the xmlrpc server
    server=http://koji.tekkamanv.com/kojihub
    ; The URL for the file access
    topurl=http://koji.tekkamanv.com/kojifiles
    ```
  
  - workdir: temporary storage directory
    
    Note: this configured path must not be the same as the KojiDir setting in the kojihub.conf file (it can be a subdirectory of KojiDir, but must not be the same as KojiDir)
    
    ```shell
    ; The directory root for temporary storage
    workdir=/tmp/koji
    ```
  
  - Authentication configuration (SSL certificates)
    
    These point to the locations where the client certificate and the CA certificate are stored.
    
    The following is the default configuration:
    
    ```shell
    ;client certificate
    ; This should reference the builder certificate we created above, for
    ; kojibuilder1.example.com
    cert = /etc/kojid/client.crt
    
    ;certificate of the CA that issued the HTTP server certificate
    serverca = /etc/kojid/serverca.crt
    ```
    
    So you can also copy the certificates to the corresponding locations, keeping the default configuration:
    
    ```shell
    sudo cp /etc/pki/koji/<common name>.pem  /etc/kojid/client.crt
    [sudo] password for tekkamanninja: 
    sudo cp /etc/pki/koji/koji_ca_cert.crt /etc/kojid/serverca.crt
    ```
    
    Note: if the koji builder is not on the same server as the one where koji hub / koji web is deployed, please copy the CA certificate and the client certificate to the __builder's /etc/kojid/ directory.__
  
  - Other settings that may need to be changed.
    
    ```shell
    smtphost=koji.tekkamanv.org
    from_addr=<common name>@koji.tekkamanv.org
    ```

# 4. Starting Kojid

**Once the builder has been added to the koji-hub system, you can start the kojid daemon on the builder. Note again: before enabling kojid on a builder, please add the builder to the koji-hub system first.**

```shell
sudo systemctl enable kojid --now
```

Please check the log file /var/log/kojid.log to make sure kojid has started successfully. If the log file shows no error messages, the builder is configured and ready to work. You can enter the system's URL in a browser and click the hosts tab; this page shows the list of builders in the database along with the status information of each builder.

# 5. Qemu Builder deployment

On the build server we use the libvirtd/virsh tools to manage images and emulators:

## a) Install software (host)

```shell
sudo dnf install libvirt libvirt-client qemu qemu-img qemu-system-riscv
```

## b) Network environment configuration

When deploying a QEMU Builder through libvirt, its network environment may need some adjustments:

### 1 Firewall configuration

__If the QEMU Builder is deployed on the same physical server as kojihub,__ this means the network communication between them goes through the virbr0 interface, and in that case you need to __open the https/http ports for this interface in the kojihub firewall__:

```shell
$ sudo firewall-cmd --list-all-zones
......
libvirt (active)
  target: ACCEPT
  icmp-block-inversion: no
  interfaces: virbr0
  sources: 
  services: dhcp dhcpv6 dns ssh tftp
  ports: 
  protocols: icmp ipv6-icmp
  forward: no
  masquerade: no
  forward-ports: 
  source-ports: 
  icmp-blocks: 
  rich rules: 
    rule priority="32767" reject
......
$ sudo firewall-cmd --add-service=https --zone=libvirt  --permanent
$ sudo firewall-cmd --add-service=http --zone=libvirt  --permanent
$ sudo systemctl restart firewalld
```

### 2 DNS configuration

The DNS server in the network needs to be able to resolve the kojihub domain name; otherwise you need to add the resolution to the /etc/hosts file of the __physical server where the QEMU Builder runs, and libvirt will pass this information on to QEMU__. For example, on kojihub:

```shell
$ ip addr show virbr0
3: virbr0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP group default qlen 1000
    link/ether 52:54:00:56:c2:c6 brd ff:ff:ff:ff:ff:ff
    inet 192.168.122.1/24 brd 192.168.122.255 scope global virbr0
       valid_lft forever preferred_lft forever
$ cat /etc/hosts
#127.0.0.1   koji.tekkamanv.com
192.168.122.1   koji.tekkamanv.com
```

**You may need to restart the builder to make sure the change takes effect**

## f) Generate the builder data disk

When Images are generated automatically with a script, necessary files such as the kojid configuration file and certificates can be injected at this point through nbd.

```shell
WORK_DIR=$(pwd)
TMP_DIR=${WORK_DIR}/.deployment
KOJI_BUILDER_DATA_MNT_DIR=${TMP_DIR}/mnt
BUILDER_NAME_PREFIX=qemu_riscv64_
NUM=001
KOJI_BUILDER_DATA_MS=${BUILDER_NAME_PREFIX}_${NUM}.data.raw 
KOJI_BUILDER_DATA_NDB_DEV=/dev/nbd8

mkdir -p $KOJI_BUILDER_DATA_MNT_DIR

#创建80G空 RAW 文件
qemu-img create -f raw ${TMP_DIR}/${KOJI_BUILDER_DATA_MS} 80G

#创建分区表
sgdisk --clear -g --new=1:4096:0 \
    --change-name=1:"kb_data" \
    --typecode=1:EBD0A0A2-B9E5-4433-87C0-68B6B72699C7 \
    ${TMP_DIR}/${KOJI_BUILDER_DATA_MS}

#格式化分区
sudo qemu-nbd -f raw  --connect ${KOJI_BUILDER_DATA_NDB_DEV} \
    ${TMP_DIR}/${KOJI_BUILDER_DATA_MS}
sudo mkfs.ext4 ${KOJI_BUILDER_DATA_NDB_DEV}p1
sudo fsck -vf ${KOJI_BUILDER_DATA_NDB_DEV}p1


#注入必要配置文件和证书#####可选步骤,可通过virsh登陆设置以下内容，详见下节#####
#挂载块设备
sudo mount -v ${KOJI_BUILDER_DATA_NDB_DEV}p1 \
    ${KOJI_BUILDER_DATA_MNT_DIR}

#注入配置文件
sudo cp -rv ${TMP_DATA_DIR}/* ${KOJI_BUILDER_DATA_MNT_DIR}
#注入证书文件
sudo cp -v ${KOJID_PEMS_DIR}/${KOJID_PEMS_PREFIX}_${1}.pem \
    ${KOJI_BUILDER_DATA_MNT_DIR}/kojid/${KOJID_PEMS_PREFIX}.pem

#修正文件属主
sudo chown -R root.root ${KOJI_BUILDER_DATA_MNT_DIR}/kojid
sudo chown -R root.root ${KOJI_BUILDER_DATA_MNT_DIR}/anchors
sudo chown root.root ${KOJI_BUILDER_DATA_MNT_DIR}/kojid/${KOJID_PEMS_PREFIX}.pem

#同步数据
sync
#卸载块设备
sudo umount ${KOJI_BUILDER_DATA_MNT_DIR}
#注入完成#####################################


sudo qemu-nbd --disconnect ${KOJI_BUILDER_DATA_NDB_DEV}
```

;if set to True, failing subtask will not automatically cancel other siblings

;log_timestamps = True
